## 时间与内容

- 使用当前日期工具确认现在的日期和时区。截止时间必须转换为包含年份、时分和 UTC 偏移的 ISO 8601 时间，例如 `2026-11-20T23:59:00+08:00`。
- 用户只说“11.2”，需要确认年份及截止时刻；日期已过时不得擅自推到明年。不明确的时间先询问，不创建猜测的提醒。
- 默认提前 4320、1440、360 分钟（3 天、1 天、6 小时），可按用户要求调整。已经过去的节点不会立即集中推送；若所有节点均已过去，和用户明确一个更短的节点。
- 从用户消息提取标题、提交要求、材料、格式、提交入口等。只保存用户提供或已核实的事实，不虚构要求。
- 为每个节点提前写好 message，涵盖任务、明确截止时间、相关要求和待检查事项。调用时将正文保存在 reminders 中，后台到点直接发送，不再调用模型。
- 创建 requestKey 使用本次用户请求的稳定标识；重试同一次创建沿用相同 key，避免重复创建。用户明确要新任务时使用新 key。

## 管理与反馈

- list 读取当前用户任务、剩余秒数和各节点发送状态。只声称工具实际完成的结果。
- update 按任务 id 提交完整新内容，新节点替换旧节点；complete/cancel 停止后续提醒。不确定是哪一项时先 list。
- 飞书目标是用户配置的一个群机器人。提醒会发送到群，内容依据用户授权的任务信息；敏感信息应确认是否适合发到群。
- feishuConfigured=false 时明确告诉用户：任务已保存，但尚不能发送，需要在服务的 .env 配置飞书 Webhook。不要索取或在回复中回显完整 Webhook 或签名密钥。
- 后端需保持运行。创建后服务会保留运行；关机/显式停止期间无法准时发送。恢复时同一任务仅补发最新一个已错过且仍未到截止日期的节点，并标记原定提醒时间；已到截止时间的节点过期，不补发“还剩一天”之类消息。
- 失败会重试，结果可 list 查看；网络响应丢失时可能出现重复送达，不能承诺严格只送达一次。
