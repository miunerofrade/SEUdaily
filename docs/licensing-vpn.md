# VPN 许可证核查

核查日期：2026-10-04。范围：当前 zju-connect 接入与 GitHub/npm 分发边界。

## 当前采用的方式

SEUdaily 自有代码维持 MIT；可选的 zju-connect 核心遵守 AGPL-3.0。当前没有修改、复制或链接核心代码。Python 管理独立可执行文件，通过命令行、标准输入输出完成认证交接，通过本地 HTTP 代理访问校园资源。普通聊天与不需要校园 VPN 的功能可独立运行。

首次连接才从上游下载固定版本并核验摘要，下载目录被 Git 与 npm 排除。上游完整许可证随我们的文本资源提供，并复制到核心旁；同时保存固定源码提交、源码归档链接和发布来源。Web 的 VPN 面板在连接按钮旁提供源码与许可证入口。自定义核心不冒用固定版本声明。

## 哪些结论可以确定

- AGPL 不会仅因为“使用了一个程序”就自动改变所有调用者的许可证。
- 自动下载与独立子进程也不保证一定属于两个独立作品。GNU FAQ 同时考察通信方式和通信语义；若互相交换复杂内部结构、紧密结合成为一个程序，结论可能不同。
- 当前可选的外部工具、标准进程接口和 HTTP 代理，为维持独立程序提供了依据。本项目据此采用上述分发边界；这不是司法认定或保证没有许可证争议。
- 核心本身不是 MIT。修改或再分发核心时，必须履行 AGPL 对相应软件的义务。仅写一个上游主页链接，不是所有分发方式下都充分的对应源码安排。

## 发布与后续更改的约束

1. GitHub 和 npm 只发布自有程序、声明与许可证文本，保持核心为可选外部程序；不要把下载缓存、认证资料或核心可执行文件放进发布包。
2. 每次升级核心，同时更新固定版本、对应源码提交和许可证文本，保留上游版权与依赖声明。
3. 若决定自行附带或镜像核心二进制，需要按 AGPL 第 6 条安排对应源码的获取方式，并核对该构建需要的源码、依赖及构建材料；不要只复用当前下载链接说明。
4. 若修改核心，除分发相关义务外，还需核对第 13 条对通过网络与修改版交互的用户提供源码的要求。该条不能简化成“任何使用代理的主程序都必须开源”。
5. 若以后复制、链接核心实现，或改为交换内部对象的紧密集成，重新评估组合作品；现在的 MIT 判断不能直接沿用。

当前没有发布 npm 包，`private: true` 保持不变。npm 的忽略规则额外排除核心和本地调试脚本；打包预览需确认许可证与声明被包含，缓存与秘密配置没有被包含。这不是完整的 npm 发布准备工作。
